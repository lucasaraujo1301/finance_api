# AGENTS.md — Project Architecture Guide

This file guides AI agents (OpenCode and similar tools) on the structure,
conventions, and rules of this project. Read it before creating, moving, or
editing any file.

## 1. Overview

FastAPI project organized into **vertical modules** (feature-based), with a
`core` module containing the shared base used by all other modules.

```
finance_api/
├── migrations/          # Generated by Alembic — do not edit manually
├── modules/
│   ├── core/             # Base: app, config, database, middleware, base model, logging
│   ├── user/              # Users, authentication (JWT), superuser access
│   ├── service_account/  # API-key based service accounts (e.g. Telegram bot access)
│   └── entry/             # Financial entries — depends on user and service_account
└── main.py               # Creates and mounts the FastAPI application
```

**Current module dependency graph (must stay acyclic):**

- `entry` → `user`, `service_account`, `core`
- `user` → `core`
- `service_account` → `core`

`user` and `service_account` must never import anything from `entry`.
`service_account` has no `router.py` of its own — its only public surface
is consumed by `entry/router.py` via `CurrentServiceAccount`.

When adding a new module, decide its position in this graph explicitly and
update it here — don't leave it implicit.

## 2. Required structure for a module

Every new module created under `modules/<name>/` **must follow exactly**
this skeleton (even if some files start out empty/minimal):

```
modules/<name>/
├── tests/
│   ├── __init__.py
│   └── ...              # integration, service, repository tests, etc.
├── router.py             # Endpoints (APIRouter) — must not contain business logic
├── models.py             # ORM models (SQLAlchemy), inherit from the Base in core
├── services.py            # Business logic / orchestration
├── repository.py         # Data access (queries), isolates the ORM
├── schemas.py             # Pydantic (request/response)
└── dependencies.py       # Depends() providers + their Annotated aliases
```

**Exception:** `router.py` may be omitted for a module with no public HTTP
surface of its own — one that exists purely to be depended on by other
modules via `dependencies.py` (see `modules/service_account/`, which has no
router; its endpoints are exposed through `entry/router.py` consuming
`CurrentServiceAccount`). Every other file in the skeleton is still
required. If a module later needs its own endpoints, add `router.py` and
register it in `main.py`.

Responsibility of each layer:

| File | Can import from | Must not contain |
|---|---|---|
| `router.py` | own module's `schemas`, `dependencies`, `services`; **another module's `dependencies.py` aliases only** (e.g. `CurrentUser`, `CurrentServiceAccount`) | SQL queries, business logic, manual instantiation of any dependency |
| `services.py` | own module's `repository`, `schemas`, `enums`/`types`; `core`; cross-module imports **only** for type annotations (e.g. referencing another module's Pydantic schema or ORM model class in a signature) | ORM/SQL details, cross-module imports used to construct or call anything at runtime |
| `repository.py` | own module's `models`, `schemas`, `enums`/`types`; `core.database`; cross-module imports **only** for type annotations | business logic, cross-module imports used to construct or call anything at runtime |
| `schemas.py` | own module's `enums`/`types`; `core` (base types) | logic |
| `models.py` | own module's `enums`/`types`; `core.models` (Base) | business logic |
| `dependencies.py` | own module's `repository`, `services`, `core`; **another module's `dependencies.py` aliases only** | endpoints, manual instantiation of cross-module dependencies |

The two "cross-module imports only for type annotations" cells above are a
narrow exception, not a backdoor: a `services.py` or `repository.py` may
import a name from another module purely to type-hint a parameter or
return value, but must never call a function, instantiate a class, or
otherwise execute anything from that import. Any cross-module value a
service or repository actually *uses* at runtime must arrive as a
parameter injected from `dependencies.py` (see section 2a) — never
imported and invoked directly. In practice this exception is rarely
needed; most cross-module dependencies flow entirely through
`dependencies.py` and never touch `services.py`/`repository.py` imports at
all.

`core/` provides cross-cutting primitives: `config.py`, `database.py`
(engine/session), `models.py` (declarative Base), `schemas.py` (base
Pydantic types, `ApiResponse`), `logger.py` (logging config), `handlers.py`
(exception handlers), `middlewares/`. No feature module should ever be
imported inside `core/`.

Pagination is provided directly by the third-party `fastapi_pagination`
library — `add_pagination(app)` is called once in `main.py`, and any
module that needs a paginated endpoint calls `apaginate(...)` in its own
`repository.py` (see `modules/entry/repository.py`) and returns a `Page[...]`
schema from its own `schemas.py`. This is normal use of the module's own
layers, not a violation of layering. What must **not** happen is building
custom pagination infrastructure (helper functions, base classes, shared
pagination logic) in `core/` or in any feature module — use the library
directly wherever pagination is needed instead of wrapping or centralizing it.

## 2a. Dependency injection convention

Every provider function in `dependencies.py` must have a matching
`Annotated` alias defined in the same file. Only the alias is ever used
elsewhere — never a raw `Depends(get_x)` call, and never the provider
function or the underlying class imported and constructed by hand:

```python
# modules/user/dependencies.py
async def get_user_service(db: AsyncDbDep) -> UserService:
    return UserService(logger, db, password_hash)

UserServiceDep = Annotated[UserService, Depends(get_user_service)]


async def get_current_user(
    credentials: Annotated[HTTPAuthorizationCredentials | None, Depends(bearer_scheme)],
    user_service: UserServiceDep,
) -> UserModel:
    ...

CurrentUser = Annotated[UserModel, Depends(get_current_user)]
```

Naming convention: `<Thing>ServiceDep` for services (`UserServiceDep`,
`EntryServiceDep`), and a plain descriptive name for identity-style
dependencies (`CurrentUser`, `CurrentServiceAccount`, `Superuser`) — not
suffixed with `Dep`.

**All dependency resolution happens through FastAPI's `Depends()` system —
nowhere in the codebase is a service, repository, or cross-module
dependency manually instantiated or resolved by calling a provider function
directly.** A module's `dependencies.py` may construct its own module's
objects (e.g. `EntryService(logger, db_session, user_service)` inside
`get_entry_service`), but every input to that constructor — including
same-module inputs like `db_session` and cross-module inputs like
`user_service` — must arrive as an injected parameter typed with its
`Annotated` alias (`AsyncDbDep`, `UserServiceDep`), never by calling
`get_db_session()` or `get_user_service()` directly, and never by importing
and instantiating `UserService` by hand.

This is what makes cross-module imports safe:

```python
# modules/entry/dependencies.py
from modules.user.dependencies import UserServiceDep   # alias, not the class

def get_entry_service(
    db_session: AsyncDbDep,
    user_service: UserServiceDep,
) -> EntryService:
    return EntryService(logger, db_session, user_service)

EntryServiceDep = Annotated[EntryService, Depends(get_entry_service)]
```

Importing the alias and letting FastAPI resolve the chain is the only
sanctioned way one module depends on another — whether that's a
`dependencies.py` composing another module's service dependency, or a
`router.py` consuming another module's identity alias directly
(`entry/router.py` importing `CurrentUser` and `CurrentServiceAccount`).

## 3. Checklist when creating a new module

1. Create the `modules/<name>/` folder with all the files from section 2,
   even if some start out as just a placeholder/`pass`.
2. Create `modules/<name>/tests/__init__.py` and replicate the test patterns
   already used in `modules/user/tests/` (fixtures, naming, reuse of
   `conftest.py` inherited from `core/tests/conftest.py`).
3. Register the new module's `router.py` in `main.py`, following the same
   inclusion pattern used for `user` and `entry`.
4. If a new table is needed, create the model in `models.py` inheriting from
   the Base in `core/models.py`, then generate the migration via Alembic
   (`alembic revision --autogenerate`) — never edit `migrations/` by hand.
5. Never duplicate infrastructure logic. Logging belongs in `core/`.
   Pagination is used directly from the third-party `fastapi_pagination`
   library in whichever module's `repository.py`/`schemas.py` needs it (see
   section 2) — don't build shared pagination helpers in `core/` or
   elsewhere.
6. Every `Depends()` provider added to `dependencies.py` must get a
   corresponding `Annotated` alias in the same file, following the naming
   convention in section 2a.
7. Decide and record the new module's position in the dependency graph in
   section 1 before writing any cross-module import.

## 4. Inter-module dependency rule (anti-cycle)

**Direction relative to `core`:** every feature module may depend on
`modules/core`; `core` must never import from a feature module. This
direction has no exceptions.

**Direction between feature modules:** *not* categorically forbidden —
governed by the explicit graph in section 1 instead. Currently `entry` is
permitted to depend on `user` and `service_account`; `user` and
`service_account` are not permitted to depend on `entry` or on each other.
When this permission exists, it is **only** ever exercised through another
module's `dependencies.py` aliases — see below and section 2a. An agent
should never read "modules must not import each other" as a blanket rule;
always check the graph in section 1 first.

- A module **must not directly import** `router.py`, `services.py`,
  `repository.py`, or `models.py` from another feature module.
- The **only** permitted cross-module *runtime* import — an import whose
  result is actually called, instantiated, or otherwise executed — is
  another module's `dependencies.py`, specifically its `Annotated` aliases
  (see section 2a). This applies whether the importer is a
  `dependencies.py` (composing another module's service into its own) or a
  `router.py` (consuming another module's identity alias, e.g.
  `CurrentUser`). The narrow type-annotation-only exception for
  `services.py`/`repository.py` described in section 2 still applies and is
  not affected by this rule.
- If A and B genuinely need to reference each other, extract the shared
  part into `core/` (or a new shared module, e.g. `modules/shared/`), so
  both depend only on it.
- For cross-module foreign keys, reference the table by string
  (`ForeignKey("entry.id")`) instead of importing the other module's model
  class, avoiding a physical cross-import.
- Prefer communication between modules via **events/callbacks** registered
  in `core` (e.g. a simple event bus) when the relationship is inherently
  bidirectional.

**Before opening an import of `modules/X` inside `modules/Y`, the agent must
check:**
1. Does `modules/X` already import (directly or indirectly) something from
   `modules/Y`? If so, **do not add the import** — refactor into `core/` or
   into a one-directional interface instead.
2. Is the import coming from `X`'s `dependencies.py`? If it's coming from
   `services.py`, `repository.py`, or `models.py` instead, refactor: expose
   what's needed as a `Depends()` provider (with its `Annotated` alias) in
   `X`'s `dependencies.py` instead of importing the internal layer directly.

All dependency resolution happens through FastAPI's `Depends()` system —
nowhere in the codebase is a service, repository, or cross-module
dependency manually instantiated or resolved by calling a provider function
directly. As noted in section 2, a `services.py` or `repository.py` may
import a cross-module name for a type annotation only; it must never call
or instantiate that import. Any cross-module value actually used at
runtime arrives as an injected parameter (see section 2a for the full
mechanics).

## 5. Tests

- `core` tests live in `modules/core/tests/`, with reusable fixtures
  exposed via `conftest.py` (e.g. `db_session`, `client`).
- Each feature module's tests live in `modules/<name>/tests/` and reuse
  `core`'s fixtures via `conftest.py` — do not recreate `db_session`/`client`
  locally.
- Suggested naming: `test_router_*.py`, `test_services_*.py`,
  `test_repository_*.py`, `test_dependencies_*.py`, mirroring the files of
  the layer being tested.

## 6. When generating code, the agent should

1. Locate the module corresponding to the task's domain (`user`, `entry`,
   `service_account`); if it doesn't exist, create it following sections 2
   and 3.
2. Place each piece of code in the file for the correct layer (table in
   section 2).
3. Mentally run the checks from section 4 before adding any import between
   feature modules.
4. Keep `main.py` as the single place that knows about all routers.
5. Never edit files inside `migrations/` manually.
